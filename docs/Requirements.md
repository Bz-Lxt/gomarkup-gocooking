## 1. 业务目标

解决年轻人两大痛点：

1. **「今天吃什么」** —— 通过可拖拽的七天饮食日历，把模糊的"想吃什么"变成确定的排期。
2. **「买菜难」** —— 把排期自动转成一张去重、合并、扣减库存、按摊位归类的买菜清单，做到「照单采购，不多买不漏买」。

**核心价值主张**：用户排完一周餐，点一次按钮，拿到一张可直接带去菜市场的清单。

## 2. 需求矛盾裁定（CRITICAL）

> 以下为 PM 在需求中检测到的内部冲突及裁定结论。后续所有 Agent **必须**遵循裁定，不得自行重新解释。

### 矛盾 C-01：常备调料过滤 vs 摊位分类含"调料"摊

- **冲突描述**：需求同时要求「自动过滤掉家里常备的调料（如盐、生抽）」和「买菜清单支持按菜市场摊位（肉类/**调料**）归类」。若无条件过滤全部调料，则"调料"摊位分组永远为空，该分类功能失去意义。
- **裁定**：过滤依据 **不是** 食材的「调料」分类属性，而是用户可配置的 **常备清单（Pantry Staples）**。
  - 系统内置默认常备清单：盐、生抽、老抽、食用油、白糖、料酒、醋、淀粉、胡椒粉（共 9 项，可在设置页逐项开关）。
  - 未被标记为常备的调料（如「郫县豆瓣酱」「泡椒」「花椒」）**正常进入清单**，归入「调料摊」分组。
  - 清单页需提供「已过滤 N 项常备调料」的可展开提示区，让用户可临时把某项重新加回清单（应对"盐用完了"场景）。

### 矛盾 C-02：保质期判定的时间基准

- **冲突描述**：需求称「冰箱已有且未过期时自动扣除」，但未定义"未过期"相对于哪一天。同一份食材可能在周一未过期、周三已过期。
- **裁定**：保质期判定基准为**该食材被实际消耗的用餐日期**，而非清单生成当天。
  - 排期在周一的菜可扣减保质期至周二的库存；排期在周三的菜不可扣减该库存。
  - 聚合引擎必须按用餐日期**升序**逐日扣减库存（FEFO，先到期先用）。
  - 对因过期而无法扣减的库存项，清单页需给出「冰箱中 X 将于 Y 日过期，建议提前食用」的提醒。

### 矛盾 C-03：数量单位不可直接相加

- **冲突描述**：需求举例「鸡蛋 2 个 + 鸡蛋 3 个 = 鸡蛋 5 个」属同单位理想情况；实际存在「猪肉 200g」与「猪肉 0.5 斤」、以及「盐 适量」这类无量纲描述。
- **裁定**：建立三层单位处理策略。
  1. **可换算**：同量纲单位归一到基准单位后相加（重量→g，容积→ml，计数→个）。
  2. **不可换算但同名**：如「香菜 1 把」与「香菜 20g」，**不强行合并**，在同一食材条目下并列展示两个子项，并标记 `needs_review`。
  3. **无量纲**：「适量」「少许」「若干」不参与数量累加，合并为单一条目并显示为「适量」。
- **禁止**：任何情况下都不得为了"看起来合并成功"而伪造换算系数（如凭空假设 1 把香菜 = 30g）。

### 矛盾 C-04：拖拽 UI 与数据模型的构建顺序

- **冲突描述**：七天日历的拖拽组件结构（餐位槽、菜谱卡、份数倍数）完全派生自 MealPlan 数据模型，UI-First 会导致返工。
- **裁定**：建议 Chief Architect 在 Phase 1 记录 **Logic-First** 构建顺序，即交换 Phase 2 与 Phase 3。最终决策权归 Chief Architect，但须在 `docs/Roadmap.md` 中写明一句话理由。

### 4.5 买菜清单生成（ShoppingList）—— 核心引擎

流水线共 6 步，顺序不可调换：

```
① 展开   MealPlan → 菜谱条目（数量 × 份数倍数）
② 归一   别名映射 + 单位换算至基准单位
③ 聚合   同食材同量纲累加；不可换算项并列保留
④ 扣减   按用餐日 FEFO 扣减未过期库存（矛盾 C-02）
⑤ 过滤   剔除用户常备清单项（矛盾 C-01），单独归档为"已过滤"
⑥ 归组   按「蔬菜细分类」或「菜市场摊位」双视图输出
```

| 编号 | 需求 | 优先级 |
|---|---|---|
| S-01 | 指定日期范围（默认整周，支持自选起止日）生成清单 | MVP |
| S-02 | 双视图切换：蔬菜细分类 / 菜市场摊位 | MVP |
| S-03 | 每项带复选框，勾选状态持久化（刷新不丢） | MVP |
| S-04 | 清单项可溯源：点开显示"来自 周一晚餐·西红柿炒鸡蛋 2个 + 周三午餐·蛋炒饭 3个" | MVP |
| S-05 | 已过滤常备项可展开并支持临时加回 | MVP |
| S-06 | 导出：复制为纯文本 / 下载 Markdown | MVP |
| S-07 | 导出：PDF 打印视图 | V2 |

### 5.1 算法正确性（硬性，不达标即 FAIL）

| 指标 | 基线 | 验证方式 |
|---|---|---|
| 同名同量纲食材合并准确率 | **100%**（确定性算法，零容错） | 单元测试，含"鸡蛋 2 个 + 3 个 = 5 个"原始用例 |
| 别名归一命中率 | **100%**（种子别名表内） | 单元测试：番茄/西红柿必须合并 |

| 过期库存误扣率 | **0%**（过期库存不得被扣减） | 边界测试：保质期 = 用餐日当天 / 前一天 / 后一天 |

## 6. 非功能约束

1. **时区**：数据库与容器统一 `TZ=Asia/Shanghai`；Go 侧禁止 `time.Now().UTC()` 直接落库，须走统一 `pkg/timeutil` 北京时间封装。
2. **日志**：禁止散落 `fmt.Println`；提供统一 `pkg/logger`（slog 封装，带 level 控制），生产环境屏蔽 debug。
3. **健壮性**：所有外部输入（HTTP body、导入数据）必须做结构完整性校验——字段存在性、类型、数值边界，不得仅靠调用方保证。
4. **API 文档**：交付 `docs/API.md`，含每个端点的请求/响应示例、参数类型说明、统一错误码表。
5. **美学**：遵循 Dribbble 标准，Tailwind + shadcn/ui，禁止工程师审美原生 HTML。
6. **端口**：开发期随机端口，`/deploy` 阶段统一为 8081+。
